## 2. 总体结构：一条流水线

解释器就是「读懂文本 → 算出结果 → 打印出来」。代码严格按这条流水线拆成 8 个职责单一的小模块，
依赖方向是单向的（`main` 在最后组装），没有循环依赖：

```
源码文本
  │  lexer.tokenize            文本 → 词（token）列表
  ▼
词列表
  │  parser.parse_program      词 → 表达式树（嵌套 Python 数据结构）
  ▼
表达式树
  │  evaluator.evaluate        表达式 → 值（心脏，特殊形式在这里分派）
  │      └─ evaluator.apply    调用过程（内置过程 / 闭包）
  ▼
值（values.py 定义）
  │  printer.scheme_repr       值 → 文本
  ▼
stdout（main.py 逐行打印）
```

| 文件 | 职责 | 行数 |
|---|---|---|
| `src/values.py` | 运行期值的定义（符号、字符串、空表、点对）+ 列表互转工具 | 67 |
| `src/lexer.py` | 词法：文本 → 词 | 54 |
| `src/parser.py` | 语法：词 → 表达式树 | 74 |
| `src/environment.py` | 环境：变量绑定表 + 指向外层环境的指针 | 23 |
| `src/printer.py` | 打印：值 → 文本 | 87 |
| `src/standard_library.py` | 内置库：spec §5 的全部内置过程 | 355 |
| `src/evaluator.py` | 求值器：`evaluate` / `apply` 互相递归 | 183 |
| `src/main.py` | 入口：读文件/标准输入，逐行打印结果 | 54 |

好处是**每一步都能独立验证**：某组用例挂了，看现象就能定位到哪一层——报「未知符号」是环境、
报「意外的 )」是语法、输出格式不对是打印、结果算错才是求值器。

## 3. 逐模块讲解

### 3.1 `values.py` —— 运行期的值

四个关键类型，都是为了绕开 Python 自身类型系统的坑：

- `Symbol(str)`：符号是 `str` 的子类。为什么要专门开一个类？因为 spec §11 明确要求
  `(equal? 'a "a")` → `#f`。如果符号直接用 `str`，它和字符串字面量就没法区分了。
- `SchemeString(str)`：字符串字面量，和 `Symbol` 互为「不同类型」。
- `Nil` 单例 `NIL`：空表 `()`。用单例对象而不是 Python 的 `None` 或 `[]`，这样 `eq?` 判同一性时
  `(eq? '() '())` → `#t` 天然成立（`is` 比较），而 `None` 要留给「无值（不打印）」这个语义。
- `Pair(first, rest)`：点对，列表就是点对链的一环。

`list_to_pairs` / `pairs_to_list` 是列表与点对链之间的转换：前者从右往左折叠成链，后者沿 `rest`
走到底，遇到非 `NIL` 结尾就抛错（说明不是真列表）。

`is_number` 特意排除了 `bool`——Python 里 `True` 是 `int` 的子类，不排除的话 `(number? #t)` 会错成 `#t`。

`is_true` 只用一句 `value is not False` 实现，对应 spec §4.4「只有 `#f` 是假，`0`、`()`、`""` 都为真」。

### 3.2 `lexer.py` —— 文本到词

一次线性扫描，产出四类词：括号 `(` `)`、引号简写 `'`、字符串值、以及其它「直到分隔符为止」的原子词。

两个值得注意的点：

- **注释**：遇到 `;` 直接 `find("\n")` 跳到行尾，注释内容根本不进 token 流。
- **字符串转义**：`\n` `\t` `\"` `\\` 四个转义在词法层就解掉了，所以后续模块拿到的
  `SchemeString` 里存的是真实字符（换行符就是换行符），打印时再由 `printer` 重新转义回去。
  字符串转义用 `for...else` 处理「扫到输入结束都没遇到收尾引号」的情况，抛 `unterminated string`。

### 3.3 `parser.py` —— 词到表达式树

递归下降。`_parse_expression` 看当前词的首字符分三种情况：`(` 进 `_parse_list`、`'` 展开成
`(quote ...)`、其余走 `_parse_atom`。

`_parse_atom` 就是 spec §3 的字面量规则，顺序很重要：先判 `SchemeString`（注意这必须放在最前，
否则会被当成普通字符串符号）、再 `#t`/`#f`、再用正则区分整数和浮点、最后兜底成 `Symbol`。

**`'x` 的简写在这里就展开成 `[Symbol("quote"), x]`**，所以求值器只需要认识 `quote` 一种形式，
不用再管简写——这是「语法糖在最早的一层剥掉」的常见做法。

顺带支持了点对写法 `(a b . c)`：`_parse_list` 里遇到独立的 `.` 词就转成 `DottedList(items, tail)`。
`DottedList` 只存在于解析阶段，`quote` 求值时会被转成和 `cons` 完全一致的点对链表示（见下）。
如果点号后面的尾巴**本身就是一个真列表**（`(list 1 2 . (3))`），解析器会直接把它折叠成真列表
`(1 2 3)`——因为「点对尾巴是列表」等价于「就是那个列表多接几项」，折叠掉可以让求值器少一种特殊情况。

### 3.4 `environment.py` —— 环境

20 多行，是整个「词法作用域 + 闭包」的基础：

```python
class Environment:
    parent   # 指向外层环境，None 表示全局
    bindings # dict[Symbol, 值]
```

`lookup` 沿 `parent` 链一直往上找，找不到才抛 `NameError`。`define` 只写当前层。

**闭包为什么能工作，全在这 20 行里**：`Closure` 保存的是「定义时」的环境对象引用；调用时新建一层
环境、`parent` 指向那个定义时环境，于是函数体里的自由变量自然就查到了定义处的绑定。

### 3.5 `printer.py` —— 值到文本

`scheme_repr` 按 spec §8 的表逐类型分派。四个细节：

- **顺序**：`True`/`False` 必须在 `int` 之前判，因为 Python 里 `isinstance(True, int)` 为真。
  这里用的是 `value is True` / `value is False`，最稳。
- **点对链打印**：先循环收集所有 `first`，走到非 `Pair` 的尾巴时——是 `NIL` 就打
  `(1 2 3)`，否则打 `(1 2 . 3)`。这样 `cons` 造出来的结构就能自动打印成正确的列表形式。
- **转义** `_escape_string`：`\` `"` `\n` `\t` 四个反向转义回去（注意反斜杠必须**第一个**替换，
  否则会把后面刚插入的转义符再转一次）。
- **兜底必须报错，不能假装**：函数最后对 `None`（无值）和任何无法识别的对象**抛 `TypeError`**。
  如果对所有未知对象一律打印 `#<procedure>`，那么一旦内部算出了不该有的对象（比如 Python 复数），
  就会被当成过程打印出来——一个「看着像正常输出」的错误答案。现在只有真正的内置过程和闭包才打印
  `#<procedure>`，其余一律报错，问题会立刻暴露而不是被掩盖。浮点用 `repr()` 打印，保住 `2.0`
  的小数点标记，与整数区分开。

`display_repr` 是给 `display` 用的：字符串不加引号，而且这个规则**递归生效**，所以
`(display (list "a" "b"))` → `(a b)`。实现上复用了同一个点对链遍历函数，只是把「渲染单个值」
的函数作为参数传进去（`_pair_repr` 传 `scheme_repr`，`_pair_display` 传 `display_repr`）。

### 3.6 `standard_library.py` —— 内置库

`create_global_environment()` 返回一个装满内置过程的全局环境。所有内置过程都包了一层
`BuiltinProcedure`（记住名字，便于报错信息），函数体的实现在同文件的私有函数里。

按 spec §5 分类，几个容易写错的：

- **每个内置过程都要自己检查参数个数**：所有内置函数都写成 `def _f(*arguments)` 的**可变参数**
  形式，进函数第一件事就是 `_require_count(arguments, N, "名字")`。为什么不能写成
  `def _car(pair)` 让 Python 去报错？因为那样报错信息会是
  `_car() missing 1 required positional argument: 'pair'`——把解释器内部的函数名和 Python 概念
  泄漏给使用者，而且还不是解释器自己的错误格式。现在 `(car)` 得到的是干净的
  `error: car: expected 1 arguments`。
- **`/` 的整数除法要「向零截断」**：Python 的 `//` 是向下取整，所以 `7 // -2` 会得到 `-4`，
  而 spec 要求 `-3`。`_truncating_quotient` 用 `abs` 先算无符号商、再补符号，精确实现向零截断。
  `quotient` 复用它。`(/ 2)`（单参数）返回 `1 / 2 = 0.5` 浮点。
- **`modulo` 用 Python 的 `%`**：Python 的 `%` 是「向下取整取模」，恰好和 Scheme 的 `modulo`
  语义一致，所以 `(modulo -7 3)` → `2`，不需要额外处理。（spec §5 写的是「整数取模」，所以
  参数先过 `_require_integers`。）
- **`expt` 绝不能用 `pow` 直接顶上**：`pow` 是 Python 的三参数内置函数，直接绑定会踩三个坑——
  `(expt 2 10 3)` 被当成模幂运算返回 `1`；`(expt -1 0.5)` 返回 Python 复数；`(expt 2.0 1024)`
  抛 `OverflowError` 直接崩出 traceback。`_expt` 先卡死 2 个参数、再检查结果是不是有限实数。
- **链式比较** `_make_comparison`：`(< 2 3 4)` 要对相邻两两都比，全成立才为 `#t`；少于 2 个参数
  返回 `#t`。每个操作数对都要求「同为数字」或「同为符号」（spec §5 说比较支持数字与符号），
  否则报错——这样 `(= #t #t)`、`(< "a" "b")` 这类没有依据的调用会明确失败，而不是碰巧返回 `#t`。
  符号之间按名字排序比较。
- **`eq?` 的三段式逻辑**（`_eq`）：空表对空表 → 真；两个数**先比类型**再按值比；符号/布尔
  同样先比类型；其余一律 `left is right`——这正好实现 spec 要求的「复合数据比同一性」，
  于是 `(eq? '(1) '(1))` → `#f`。数字也要比类型，是为了让 `eq?` 与 `equal?` 口径一致：
  `(eq? 1 1.0)` 和 `(equal? 1 1.0)` 都返回 `#f`，不会出现「`eq?` 为真但 `equal?` 为假」。
- **`equal?` 先比类型**：`type(left) is not type(right)` 就返回 `#f`，一举解决 `(equal? #t 1)` →
  `#f` 和 `(equal? 'a "a")` → `#f` 两个坑。`Pair` 递归比较，`NIL` 返回真。
- **`abs` / `zero?` / `even?` / `odd?` 要先查类型**：`number?` 已经不把布尔当数字，但 `abs(#t)`
  如果直接调用 Python 的 `abs` 会得到 `1`（Python 里 `True` 就是整数 `1`）。所以这几个都先过
  `_require_numbers` / `_require_integers`，与 `number?` 的口径保持一致。
- **`list?` 防环**：`_is_proper_list` 用一个 `seen` 集合记录走过的点对 id，万一遇到环形结构
  也不会死循环。
- **`procedure?` 为什么用类名判断**：`Closure` 定义在 `evaluator` 里，而 `evaluator` 要 import
  本模块——直接 import 会形成循环依赖。所以这里用 `type(value).__name__ == "Closure"` 来识别。
  这是本文件里最「取巧」的一处，代码里写了注释说明，属于有意的权衡。
- **`display` / `newline`**：写成闭包捕获了 `output`（传入的 `sys.stdout`），每次写后 `flush`，
  并且**返回 `None`**——这正是 spec §2「结果为 `None` 时不打印」能成立的前提。外面又包了一层
  做参数个数检查（`newline` 必须 0 个参数）。

### 3.7 `evaluator.py` —— 心脏

整个解释器最核心的两个互相递归的函数：

```python
evaluate(expression, environment)   # 表达式 → 值
apply(procedure, arguments)         # 过程 + 实参 → 值
```

`evaluate` 遇到函数调用就调 `apply`；`apply` 执行闭包函数体时又调回 `evaluate`。想通这个循环，
解释器就成了一半。

**`evaluate` 的分派顺序**（自上而下，每一条对应 spec 的一类东西）：

1. `NIL` / 布尔 / 字符串 / 数字 → **自求值**，原样返回
2. `Symbol` → 查环境
3. `DottedList` → 报错（不完整的点对不能当函数调用）
4. 不是 `list` → 报错
5. 空 list → `NIL`（对应 `()`）
6. 首元素是 `Symbol` 且命中特殊形式表 → 交给对应的处理函数
7. 其余 → **应用序求值**：先求值操作符，再**从左到右**求值全部实参，`apply`

**`apply` 只有三种情况**：内置过程直接调用；闭包则先检查实参个数是否与形参一致，然后新建一层
环境把实参绑到形参名上、`parent` 指向闭包保存的**定义时环境**，再按 `begin` 语义求值函数体；
其余抛「试图调用非过程」。

**九个特殊形式**（spec §4），关键是各自的求值顺序**都不一样**：

| 特殊形式 | 求值顺序要点 | 实现函数 |
|---|---|---|
| `quote` | 不求值，原样返回数据（但要转成点对链） | `_evaluate_quote` |
| `if` | **只求值一个分支**；缺假分支且测试为假 → `None` | `_evaluate_if` |
| `cond` | 从上到下找第一个真测试；无表达式时返回测试值本身；全不匹配 → `None` | `_evaluate_cond` |
| `and` | 从左到右，遇 `#f` 立刻返回 `#f`（短路）；`(and)` → `#t` | `_evaluate_and` |
| `or` | 从左到右，遇非 `#f` 立刻返回它（短路）；`(or)` → `#f` | `_evaluate_or` |
| `define` | 先求值右侧再绑定；返回被定义的符号名（顶层会打印） | `_evaluate_define` |
| `lambda` | **函数体此时不求值**，只打包成闭包 | `_evaluate_lambda` |
| `let` | 所有绑定表达式在**外层**环境先求值完（并行绑定），再在新环境跑体 | `_evaluate_let` |
| `begin` | 从左到右，返回最后一个 | `_evaluate_begin` |

几个具体实现点：

- **`quote` 的数据要转成和 `cons` 一致的点对链**。`_quote_to_value` 递归把 Python `list`
  转成 `Pair` 链，于是 `'(1 2 3)` 和 `(list 1 2 3)` 得到**同一种**运行期表示，`car`/`cdr`/
  `equal?` 不用为两者各写一套。这是 spec §11 最后一条「避免打印成 `(1 2 . 3)` 或卡死」的正解。
- **`and` / `or` 的返回值不能用 `bool` 收尾**：`and` 全为真时返回**最后一个表达式的值**（不是 `#t`），
  `or` 返回第一个非假值本身。代码里用 `result is False` 判断短路，绝不用 `if not result`
  （否则 `0` 和 `()` 会被误判为假）。
- **`define` 的函数简写**：`(define (f x) body)` 就是把 `target` 是 list 的情况翻译成
  `Closure(参数, 体, 当前环境)`，等价于 `(define f (lambda (x) body))`。
- **`let` 的并行性**：`values.append(evaluate(binding[1], environment))`——注意这里传的是
  外层 `environment` 而不是新建的 `local`，所有初始化表达式都在外层求值，绑定之间互不可见。
  之后才建 `local` 并批量绑定。
- **`cond` 的 `else`**：检查它必须是最后一个子句，否则报语法错；`(cond (else 42))` 也就能正常工作。
- **形参校验** `_validate_parameters`：必须是符号，且不能重名。

### 3.8 `main.py` —— 入口

`main()` 三件事：建全局环境（传入 `sys.stdout`）→ 有文件参数就按顺序逐个 `run_source`
（**共用同一个环境**，所以后一个文件能看到前一个文件的 `define`），没有参数就读标准输入 → 返回退出码。

`run_source` 就是 spec §2 的 CLI 约定：对每个顶层表达式求值，**结果不是 `None` 才打印一行**
（`display`/`newline` 返回 `None`，所以不打印）。

顶层还统一捕获异常，把错误写到 `stderr` 并返回退出码 1——评分器据此区分「输出不符」和
「解释器报错」。捕获清单里的每一项都对应一类真实会发生的失败：

| 捕获 | 对应的情况 |
|---|---|
| `ValueError/TypeError/NameError/SyntaxError` | 未知符号、调用非过程、参数个数/类型不对、语法错误 |
| `ArithmeticError` | 除以零、`(expt 2.0 1024)` 这类结果溢出的浮点运算 |
| `RecursionError` | Scheme 程序递归过深（spec §10 明确不做尾调用优化） |
| `OSError` | 命令行给的 `.scm` 文件不存在或读不了 |

**为什么要专门处理递归深度**：解释器是递归实现的，一层 Scheme 递归要消耗好几层 Python 栈帧，
Python 默认的 1000 上限大约只能支撑 150 层 Scheme 递归——一个写得不夸张的递归程序就可能撞上。
所以入口把上限提到 `RECURSION_LIMIT = 20000`（实测约 3000 层 Scheme 递归可用），并且**兜底
捕获 `RecursionError`**：超过之后给出干净的 `error: maximum recursion depth exceeded`，
而不是甩出一屏 Python traceback。两件事缺一不可——只提上限不兜底，程序仍会崩；只兜底不提上限，
能跑的深度又太浅。

## 4. spec 陷阱 → 代码位置对照表

这份表可以当成自查清单：每一行都是 spec 明确点名的坑，右边是解决它的地方。

| spec 里的坑 | 期望 | 在哪里解决 |
|---|---|---|
| `(/ 7 2)` 得到 `3.5` | 整数相除得整数商 | `standard_library._truncating_quotient` |
| 负数商 `(/ -7 2)` | `-3`（向零截断，不是 Python 的 `-4`） | 同上（用 `abs` + 补符号） |
| `(modulo -7 3)` | `2`（向下取整语义） | `standard_library._modulo`（Python `%` 天然一致） |
| `(/ 2)` | `0.5` 浮点 | `standard_library._divide` 单参数分支 |
| `(and #f (/ 1 0))` 报错 | `#f`，右边不该执行 | `evaluator._evaluate_and`（逐项 `is False` 短路） |
| `(or #t (/ 1 0))` 报错 | `#t` | `evaluator._evaluate_or` |
| `(equal? #t 1)` 判成相等 | `#f` | `standard_library._equal`（先比 `type`） |
| `(equal? 'a "a")` 判成相等 | `#f` | `values.Symbol` vs `values.SchemeString` + `_equal` 比类型 |
| `(eq? '(1) '(1))` 判成相等 | `#f`（比同一性） | `standard_library._eq` 兜底 `left is right` |
| `(eq? '() '())` | `#t` | `values.NIL` 单例 + `_eq` 首行 |
| 列表打印成 `(1 2 . 3)` 或卡死 | `(1 2 3)` | `evaluator._quote_to_value` + `printer._pair_repr` |
| `(number? #t)` | `#f` | `values.is_number` 排除 `bool` |
| `let` 绑定串行求值 | 并行绑定 | `evaluator._evaluate_let`（在外层环境求值） |
| 闭包用例失败 | `lambda` 要记住定义时环境 | `values.Closure.environment` + `environment.Environment.parent` |
| `(if #f 1)` | 不打印（`None`） | `evaluator._evaluate_if` + `main.run_source` 的 `is not None` |
| 只有 `#f` 是假 | `(not 0)` → `#f` | `values.is_true` 只用 `is not False` |

### 4.1 额外补上的坑（不在 spec 明列，但属于同一类）

这些是测试过程中挖出来的，性质都是「spec 允许的输入不该崩、不该给错值」：

| 现象 | 原因 | 现在怎么处理 |
|---|---|---|
| `(expt 2 10 3)` → `1` | 直接绑定 Python 的三参数 `pow`，被当成模幂运算 | `standard_library._expt` 卡死 2 个参数 |
| `(expt -1 0.5)` → `#<procedure>` | 结果是 Python 复数，被打印器的兜底当成过程 | `_expt` 检测复数后报错；打印器兜底改为抛错 |
| `(expt 2.0 1024)` 甩 traceback | 浮点溢出抛 `OverflowError` | `_expt` 检测非有限值 + 入口捕获 `ArithmeticError` |
| `(abs #t)` → `1` | Python 里 `True` 就是 `1`，绕过了类型检查 | `_abs`/`_expt` 先过 `_require_numbers` |
| `(cons 1)` 报 `_cons() missing ...` | 内置函数写成固定参数，Python 先于我们的检查报错 | 全部改成 `*arguments` + 显式 `_require_count` |
| `(= #t #t)`、`(< "a" "b")` 返回 `#t` | 直接调 Python 比较，任何类型都能比 | `_make_comparison` 要求「同为数字」或「同为符号」 |
| `(eq? 1 1.0)` 为真但 `(equal? 1 1.0)` 为假 | 两处对「数字」的类型口径不一致 | `_eq` 也先比类型，两个谓词口径统一 |
| `(list (if #f 1) 2)` → `( 2)` | 无值 `None` 在结构里打印成空洞 | 打印器遇到 `None` 直接报错 |
| `(display (list "a" "b"))` → `("a" "b")` | `display` 去引号没有递归进结构 | `display_repr` 递归渲染点对链 |
| 文件参数不存在 → traceback | 入口没捕获 `OSError` | 入口捕获 `OSError` |
| `(append '(1 2) 3)` 报错 | 要求所有参数都是真列表 | 只有最后一个参数允许非列表（cons 到它上面） |
| `(list 1 2 . (3))` 报错 | 点对尾巴是列表时没归一化 | 解析器把「尾巴是真列表」的点对折叠成真列表 |

## 5. 做过的验证

除了跑官方评分器的 12 组验收用例，另外做了四类独立验证，都是为了覆盖官方用例没碰到的角落：

1. **12 组官方验收用例**：全部通过。
2. **`example/` 六个示例**：逐个运行，输出与文件里注释标注的期望输出**逐行一致**
   （含 `06_io.scm` 的 `display` 不换行、字符串带引号与 `\n` 转义打印）。
3. **spec 逐条测试（257 条）**：期望输出全部按 spec 手工推导，不是从实现反推的。其中 19 条是
   「必须干净报错」的用例，要求给出解释器自己的 `error: ...` 而不是 Python traceback。
   → 全部通过。
4. **随机差分测试（多个随机种子，每次 1200 条程序）**：用一份按 spec 直接写的 Python 模型当参照
   （向零截断的除法、floor 取模、链式比较、`and`/`or` 返回**值**而非布尔），随机生成嵌套的
   算术/比较/布尔/`if` 表达式，两边逐字节对比输出。→ 零差异。
   这一轮先抓出的是**模型自己**的 bug（把 `(not 0)` 按 Python 语义写成真，而 spec §4.4 规定只有
   `#f` 是假），修正模型之后实现零差异——反过来也印证了实现是对的。
5. **另一份独立解释器的差分对照**：另写一个完全独立的参考实现，配 38 个探针程序加 87 条补充
   程序，两边逐字节对比。这一步直接促成了第 4.1 节里 `append` 尾参和点对尾巴归一化这两处改进。

第 4.1 节列出的问题，都是从上面第 3、4、5 类验证里发现的，其中 `expt` 那一组最严重：
`(expt 2.0 1024)` 会直接甩出 Python traceback，`(expt -1 0.5)` 会打印出
`#<procedure>` 这种「看着正常、其实完全错」的答案。
